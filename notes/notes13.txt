Scheduler should be empty


Key insight, we cannot toggle timer interrupt mask based on default/disk interrupt handler. This is a leak. So timer interrupt mask is always opposite than the rest.
This means that timer interrupts cannot be handled within the time slice.

Another insight. We can only allow disk interrupt to run once during this window. This is because we need to ensure that the defaulthandler is the one that terminates. The termination signal, sent went the time slice is over is used to change public info (tI handler mask), so this needs to be public. If disk handler is the last to run it will send the signal and it will reveal that it was scheduled (since no presence of disk interrupts would mean the default handler was scheduled). So we need to enforce that the time slice ends with default handler.
Another way to implement this is to set the time slice to two and ensure that after timer has run out, the handler runs the termination routine. The simplest fix however is that a disk interrupt handler does not unmask itself after it is done. So the mask should follow timer interrupt except for when output is from the timer interrupt. That is incorrect, then defaultI would also block. We need an equality check for dI.
Actually this is a good fix, if we wanted a post handler routine that ran the default handler, we would try to implement it by distignuishing the case where disk interrupt handler outputs notify together with true, in which case we should jump the default handler for two iterations before returning to user space. However, if instead of disk interrupt handler we were at the default handler when time ran out we would still need to do the post routine (as the length of execution would leak otherwise) and we cannot by the output of default handler determine if counter has just finished or we are in the post routine. This could be implemented but it requires the default handler to have a larger output type than disk interrupt handler, and I like the symmetry as it is.




Idea for moving counter to state

1. Hardware Level: The Interrupt Controller (Best for Real-Time/Hardware Guarantees)
If you want guaranteed, hard-real-time enforcement that cannot be bypassed or delayed by software execution, the counter must be implemented in the Interrupt Controller (such as the ARM GIC, RISC-V PLIC/CLIC, or x86 APIC) or a custom Hardware Interrupt Throttler block.

Where: In the interrupt controller’s register space (as MMIO-mapped registers).

How it works:

When an interrupt is dispatched to the CPU, a hardware timer is initialized with the "time slice" value.

The timer decrements while the CPU is executing in interrupt context (which the hardware can track by monitoring the interrupt acknowledgment and End-of-Interrupt (EOI) signals).

If the counter reaches zero before the EOI is received, the hardware logic triggers an internal mask signal, disabling the distributor or the CPU interface from forwarding any further interrupts to the processor.
