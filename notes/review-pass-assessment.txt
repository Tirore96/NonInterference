1. NEW FINDINGS (not commented yet, and more important than most comments)
--------------------------------------------------------------------------

N1. Intro overclaims the attacker.  [high]
    intro.tex, "We prove this variant non-interfering ... even to an attacker who
    sees, at every step, which process in the pool ran, the scheduler and the
    handlers included."
    False as stated: the attacker does NOT see which secret handler ran. That is
    the whole point (whether public, which private). out_equiv wraps the disk and
    NOP slots in eqmaybe({H}, private), so None is unobservable to L there.
    Fix: "which process ran, except which of the two secret handlers".

N2. II-C overclaims the constructor correspondence.  [high, my own text]
    background.tex, "each process constructor has a matching constructor on
    equivalences (Theorem 1)". Not true for out, map and loop: they introduce no
    equivalence constructor. The correspondence holds for par (eqpair), swi
    (eqpair_LR on input, eqmaybe(Aw(true,B), O) on output), maybe (eqmaybe(empty, I)
    on input) and sta (eqpair_R(V, I) inside, eqpair(V, O) outside).
    Fix: "the constructors that combine or gate processes each have a matching
    constructor on equivalences". This also shapes comment B1 below.

N3. "Phase" vocabulary is stale in III-C too, not only in V.  [low]
    model.tex, slice-counter bullet: "tracks the phase of a time slice ...
    (Fig. 7)". Same issue as comment P6; fix both together.

N4. One-step handlers are explained three times.  [low]
    IV-B footnote, V-C last paragraph, conclusion "Limitations". Keep V-C, make
    the other two one-clause pointers.

N5. Page budget.  [check]
    The paper is 12 pages without the red comments. Check CSF's limit and
    whether the appendix and references count; several comments below add
    figures (constructor table, proof tree, Fig. 1 redraw).


2. COMMENTS TO REVISE
---------------------

I1  Fig. 1 vs Fig. 6 (intro).  REVISE: overstated.
    The comment says there are three different runs. There are two: Fig. 1 and
    the mechanised counterexample agree (interrupt before step 1, inserted at
    position 0 in model_immediate_not_NI; handler at 2-3). Only Fig. 6 differs
    (interrupt after step 1, handler at 3-4, as in immediate_with_dI').
    Recommendation: make Fig. 1 the two ordinary rows of Fig. 6 drawn in the
    strip style (same run, same visual language), and keep the counterexample
    as is: it is a minimal trace, and IV-A can say so in one clause.

B1  Constructor table (II-C).  REVISE.
    Sound idea, but the table needs input and output columns (swi and sta
    change both sides), and out/map/loop rows say "no new constructor" (see N2).

B3  Theorem 1 "shrink each item".  REVISE: risky.
    Theorem 1 is the formal statement the rest relies on; shrinking items
    loses precision. Keep it complete; only move the theorem names into the
    constructor table, and let the table carry the intuition.

M4  Shade the state listing, drop Table II.  REVISE.
    Shading a code listing field by field is awkward: the current pid is half
    public (inl vs inr) and half private (which secret handler). Better: keep
    Table II but write its equivalences out (as P3 says), and in III-C only
    add "the inl side is exactly S". Drop the "Table II redundant" part.

P1  Proof tree figure (V).  REVISE: correct the details first.
    The term is map / loop / map / sta / map / maybe / pool, and each slot is
    swi (maybe (map ... proc)) (models.v, reactive_system and slot_procs). So
    maybe_NI applies twice (idling pool and each slot), and map_NI several
    times. The V text names maybe_NI only "for the idling pool". The figure is
    still a good idea, but it must show this structure accurately or it will
    mislead.

P5  Theorem 4 wording.  REVISE.
    "not all masks are set" is exactly the guard of initiate_next (masks_set),
    so the formal condition must stay. Keep it and add the gloss "i.e. no
    handler is running" rather than replacing it.

G1  Drop the Rocq listing in VI.  REVISE: a choice, not a defect.
    The listing shows the discharged statement verbatim, which supports the
    "mechanisation is ground truth" goal. Listing and Table III do overlap:
    keep one. I lean to the table, but this is the author's call.

I6  "one substantial obligation" vs two.  REVISE: the wording, not the count.
    II-D and V say two side conditions; the intro and VI ("the one hard
    obligation") mean the hard one (fv_NI). Unify as "two side conditions, one
    of them hard (fv_NI)".

V2  "only notational" (VII) vs "alternative definition" (II-B).  REVISE.
    The author asked for the line in II-B, so keep both, but use the same word
    in both places.


3. COMMENTS TO WITHDRAW
-----------------------

M5  "Rules 1-4 can be read off the U/T/S diagrams; drop the enumerate."
    WITHDRAW. The priority rule is generic (initiate_next), the diagrams are
    per policy, and the diagrams do not show "return to the interrupted
    process vs. the scheduler" or "current process continues". The enumerate
    carries information the figures do not.

D2  "Does immediate_init need a listing?"
    WITHDRAW. The author asked for both initial states to be shown in full,
    and IV-A/IV-B are meant to be parallel (concept, code, run, theorem).
    Removing one listing breaks the parallel.

D3  "Proof sketch repeats the walk-through."  DOWNGRADE to optional.
    The walk-through follows the Fig. 6 run (interrupt after step 1); the
    sketch follows the counterexample trace (interrupt before step 1) and
    adds insertion and determinism. The overlap is one sentence about
    initiate_next. The author explicitly asked for the more formal sketch.
