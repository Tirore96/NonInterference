Project status:

We went away from previous model where the scheduler was a lambda in a wrapper around the process pool because of 1) it was missing timing interrupts, therefore less realistic and 2) An outer sta construct with an inner swi was causing problems in the NI proof.
The new idea was to keep the state inside the scheduler as its own process in the process pool, and this addressed both issues.

Issues with having the scheduler be its own process in the pool:

- The trace of the pool becomes unrealistic because of interleaved scheduler outputs.
An interchangable scheduler (good vs bad) that can be plugged into the pool means we need it as a decider for which process continues after receiving a disk interrupt (good = current process, bad = handler). If the scheduler is an actual process (as opposed to a lambda in a wrapper around the process pool) the choice will come as an output (public, but that's irrelevant) and this would offset a subsequent output of the public process, making the pool as a whole interfering. To fix this, outputs in the trace of the process pool would have to always alternate between scheduler output (the choice) and running process (the chosen).

- The trace of the pool becomes unrealistic because of simultaneous outputs.
In the former scenario the pool was cooperative, returning control to the scheduler at every turn. If we consider a non-cooperative pool, the scheduler turns off active processes resulting in simultaneous outputs (Some scheduler_out, Some active_process_out,...). This is not realistic for modeling the cpu jumping to different parts of memory to execute code.

If we want a realistic process trace, the model itself becomes less realistic because the scheduler is an interchangable lambda rather than an interchangable process.

The lambda approach itself also has an issue, but this one seems solvable.
In this design we have a sta around the process pool that introduces the state of which process is currently running.

If our model was of the form sta f g v p and we try to show it is NI.

By the sta theorem it is NI if p is NI.

NI (eqpair_R VRel IRel) ORel p   ....(other assumptions)....
-------------
NI IRel (eqpair VRel ORel) (sta f g v p)

For NI of p to hold, output may not visibly change when we insert into a trace input (v,I) where I is distinguished.
This is too strong and our model will not satisfy it. Some state inputs to p can and should alter public output since state controls the schedule. To be non interferring the model must be implemented such that if I is distinguished (disk interrupt), the accompanying v in the input (v,I) to p should not be affecting this schedule. If I is not distinguished, then inputting (v,I) to p may affect later output.
We have a dependence between I and v that cannot be expressed by existing eqpair relation combinators.

I think it can be expressed as introducing a new relation combinator eqpair_P VRel IRel, where (v,I) is distinguished if P (v,I) which we set P(v,I) := I distinguished /\ (exists v', f I v' = v). If f maps state to neutral state values (those that do not visibly alter output) whenever I is distinguished, we avoid having to reason about problematic state input to p.

NI (eqpair_P VRel IRel) ORel p   ....(other assumptions)....
-------------
NI IRel (eqpair VRel ORel) (sta f g v p)

Continuing, this dependence between (v,I) means that when v is later translated to a boolean it will only be true (thus having an effect) if I is not distinugished. We can therefore extend the idea to the swi theorem. This is necessary because the existing swi theorem has a conclusion with an input relation built with eqpair_LR BRel IRel, but during our proof we arrive at an obligation of the form eqpair_P VRel IRel.

(forall l, aware BRel true l) 	    NI IRel (eqpair_R BRel ORel) p
------------------------------------------------------------------ (P (b,I) := I distinguished /\ b = false)
NI (eqpair_P BRel IRel) (eqmaybe ORel) (swi b p)
