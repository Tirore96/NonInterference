\section{Two Interrupt Policies}\label{sec:designs}

Two interrupt policies instantiate the model: \m{model_immediate}, which
leaks (\cref{sec:leak}), and \m{model_sliced}, which does not (\cref{sec:sliced}).
Both are exercised on the same concrete system. Its public user process emits
\code{Get} whenever it runs, its private user process emits \code{Sys} when the disk
handler has notified it and \code{Idle} otherwise, and the scheduler alternates between
them. Handlers take $\mathit{runtime} = 2$ steps.
\Cref{fig:policy-ordinary,fig:phases} draw the two policies over the three
kinds of step of \cref{sec:processes}, and \cref{fig:run-ordinary,fig:run-sliced} run
them on the same inputs.

\subsection{Immediate interrupt handling, and the leak}\label{sec:leak}

The immediate policy \m{model_immediate} services an interrupt as soon as no handler is running
(\cref{fig:policy-ordinary}). A pending timer interrupt takes the system from U to T,
and a pending disk interrupt takes it to S, from U or from T, at whatever step it
arrives. Each completion unmasks everything and moves on to the next pending handler,
or back to U. The bold arrows into S are the leak: they are rule 2 of
\cref{sec:state} at work, and the secret decides when S is
entered and how long it lasts.

The initial state starts in the public user, outside any slice, with all bits of the
interrupt controller clear (fields as in \cref{sec:global-state}, with one (pending,
mask) pair per handler):
\begin{lstlisting}
immediate_init :=
  ((inr 3, 3),          (* public user *)
   (false, (0,           (* slice counter *)
    ((false,false),      (* NOP *)
     ((false,false),     (* disk *)
      (false,false)))))) (* timer *)
\end{lstlisting}

The second stage of the service policy is the identity, and the first reacts to any
handler finishing:
\begin{lstlisting}
observe_handler_output o v :=
  if is_ir_out_done o is Some ir then
    let v := unset_masks v in
    if ir is timer_irq then update_re_sched v true
    else v
  else v
\end{lstlisting}
In the output \code{o}, \m{is_ir_out_done} names the handler, if any, that emits
\code{Notify}. The service policy then unmasks everything, and after the timer handler
also requests a reschedule. It thus reads the output of whichever handler completes,
the disk handler's included.

In the run with the disk interrupt (\cref{fig:run-ordinary}), the disk handler takes
steps 3 and 4 from the public user. The pid of each step is computed at the output of the step before (\cref{sec:state}).
The disk interrupt arrives after step 1 and only sets the disk pending bit, so step 2
still belongs to the public user. At the output of step 2, \m{initiate_next} finds
the disk handler pending and unmasked and starts it, setting all masks: U to S. The
timer interrupt that arrives meanwhile stays pending until the disk handler emits
\code{Notify} at step 4: S to T. The timer handler's completion at step 6 requests a
reschedule: T to U, where the scheduler hands step 8 to the private user. Without the
disk interrupt the system never enters S.

\input{sections/fig-io}
To state the leak we classify what the system receives and emits. Its input
type \m{T_in} is a sum, like the
current pid of \cref{sec:global-state}: \code{inl} is the disk interrupt and
\code{inr} the timer interrupt. Its output type is the pool's six-tuple
\m{T_out}.

\medskip
\noindent\begin{minipage}{\linewidth}
\begin{definition}[Input and output equivalences]\label{def:io}
The input equivalence $\Ein$ (\m{in_equiv}) and the output equivalence $\Eout$
(\m{out_equiv}) are
\begin{align*}
\Ein &\triangleq \priveq + \pubeq, \\
\Eout &\triangleq (\pubeq + \one^\Lo) \times (\priveq + \one^\Lo) \times (\pubeq + \one^\Lo) \\
&\quad{} \times (\priveq + \one^\Hi) \times (\priveq + \one^\Hi) \times (\pubeq + \one^\Lo),
\end{align*}
one factor per slot of \cref{fig:io}, with $\times$ associating to the right, as the
output nests.
\end{definition}
\end{minipage}
\medskip

Under these equivalences the disk interrupt is hidden from the attacker and the timer
interrupt is public. Of each output the attacker sees whether the slot ran and its value on the
white slots of \cref{fig:io}, only whether it ran on the light slot, and nothing
on the dark ones.
So the attacker sees when the U and T steps happen. On an S step it sees that those
slots are all empty, which shows that a secret handler ran and leaves open
which. This is the view the proof works with (\cref{sec:proof}), and
\cref{sec:gating} shows that the proof forces this shape.

The step into S and the time spent there are thus visible. For the attacker to learn
nothing, both must be fixed by public events; what runs inside S may depend on
the secret. The immediate policy fails this:

\begin{theorem}[Leak, \m{model_immediate_not_NI}]\label{thm:leak}
For the concrete system,
\[
\mathsf{model\_immediate\_concrete} \notin
  \NI(\Ein,\, \Eout).
\]
\end{theorem}

\begin{proof}[Proof sketch]
The counterexample is the shortest trace that shows the gap: the disk interrupt
arrives before step 1, one step earlier than in \cref{fig:run-ordinary}. Let $p$ be the model and $o_G$ the output in which only the public slot is set, to
\code{Get}. The model performs $\perf{p}{!o_G.!o_G}{\Lo}$. The disk interrupt is
unobservable at $\Lo$, so insertion demands $\perf{p}{?\mathsf{disk}.!o_G.!o_G}{\Lo}$.
Reduction is deterministic (\cref{sec:background}): $p$ has exactly one input step on
\textsf{disk} and every process exactly one output step, so we only need to follow
that run. The input step $\stepI{p}{\mathsf{disk}}{p_1}$ sets the disk pending bit and
leaves the pid at its initial value, the public user. So the output step
$\stepO{p_1}{o_1}{p_2}$ emits $o_1 = o_G$, and at its end \m{initiate_next} finds the
disk handler pending and unmasked and sets the pid to the disk handler: U to S. The
next output step $\stepO{p_2}{o_2}{p_3}$ is the disk handler's, so $o_2$ has
\code{None} in the public slot, and $o_2 \not\Eout_\Lo o_G$.
\end{proof}

The counterexample turns on the public slot alone, so the leak needs nothing beyond
the public user's output. The \emph{public view} of a model \code{m},
\code{map id public_output m}, keeps only that slot, as a value of type
\code{Opub + 1}, at the equivalence $\pubeq + \one^\emptyset$
(\m{out_equiv_publicview}):

\begin{corollary}[Public-view leak,\newline \m{model_immediate_publicview_not_NI}]\label{cor:leak-publicview}
For the concrete system,
\[
\mathsf{publicview}\;\mathsf{model\_immediate\_concrete}
  \notin \NI(\Ein,\, \pubeq + \one^\emptyset).
\]
\end{corollary}

\begin{proof}
The counterexample of \cref{thm:leak}: $o_2$ and $o_G$ differ in the public slot.
\end{proof}

To present results at the level of user space, we abstract from interrupts and
scheduling to what the user processes emit. The \emph{user view} of a model \code{m},
\code{map id parse_output m}, keeps only the two user slots: \m{parse_output} maps an
output to a value of type \code{(Opub + Opriv) + 1}, for the user processes' output
types \code{Opub} and \code{Opriv}: the public user's as
\code{Some (inl v)}, the private user's as \code{Some (inr v)}, and any other as
\code{None}.

The user view needs its own equivalence. At $\Lo$ a private-user output and \code{None}
are both hidden, so a plain sum would relate them and hide whether the private user
ran, and we use $\privvis$ for the private user instead.

\begin{definition}[User-view equivalence]\label{def:userview}
The user-view equivalence $\Euser$ (\m{out_equiv_userview}) is
\[
\Euser \triangleq (\pubeq + \privvis) + \one^\emptyset.
\]
\end{definition}

To the attacker, the user view loses only public information: the outputs of the
scheduler and the timer handler, and, on a step where no user process ran, whether
the step was theirs or an S step. The attacker still sees when the private user runs,
and the leak is visible in the user view as well:

\begin{corollary}[User-view leak,\newline \m{model_immediate_userview_not_NI}]\label{cor:leak-userview}
For the concrete system,
\[
\mathsf{userview}\;\mathsf{model\_immediate\_concrete}
  \notin \NI(\Ein,\, \Euser).
\]
\end{corollary}

\begin{proof}
The missing \code{Get} is a public-user output, which \m{parse_output}
keeps, so the counterexample and the proof are those of \cref{thm:leak}, with
every output passed through \m{parse_output}.
\end{proof}

\subsection{Sliced interrupt handling}\label{sec:sliced}

The sliced policy removes the bold arrows. It runs the secret handlers only in
\emph{time slices}: S is entered only when the timer handler completes, and the
system stays there for a fixed number of steps (\cref{fig:phases}). A slice holds
exactly $\mathit{runs}$ handler runs ($\mathit{runs} = 2$ in the concrete system), and
when no disk interrupt is pending the NOP handler takes the run, so a slice is the
same whether or not a disk interrupt is waiting. Each part of the policy below
removes an arrow of \cref{fig:policy-ordinary} or fixes how long S lasts.

\input{sections/fig-sliced}

A slice is timed by the slice counter, which counts the output steps until the slice
closes. Outside a slice, in U and T, it is \code{0}. The output that opens a slice
loads it with $\mathit{runs}\cdot\mathit{runtime}+1$ and also ticks it, so it reads
$\mathit{runs}\cdot\mathit{runtime}$ on the first step of the slice and \code{1} on the
last, and the $\mathit{runs}$ handler runs fill exactly these steps. The slice closes
at the output of its last step.

The initial state \m{sliced_init} is \m{immediate_init} with the disk and NOP masks
set, so no disk interrupt can take the system from U to S, and the timer unmasked.

The service policy uses both stages of \cref{sec:state}, \m{observe_timer_output}
and then \m{tick_slice}; \m{sliced_service} is their composite. The first stage is the
immediate policy's observation restricted to the timer handler, whose output
is public; hence its name. It keeps the
reschedule and, instead of unmasking, opens the slice, the only way from T to S:
\begin{lstlisting}
observe_timer_output runtime runs o v :=
  if tI_out o is Some Notify then
    update_re_sched
      (update_slice_count v
         (runs * runtime).+1)
      true
  else v
\end{lstlisting}
The reschedule returns control to U, through the scheduler, once the slice is over.
The second stage
advances an open slice by one step:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
tick_slice runtime v :=
  match get_slice_count v with
  | 0    => v
  | 1    => close_slice v
  | n.+2 =>
    let v := update_slice_count v n.+1 in
    if slice_at_boundary runtime n.+1
    then queue_secret_run v else v
  end

queue_secret_run v :=
  update_ir_pending (set_tI (unset_masks v))
    nop_irq true
\end{lstlisting}
\end{minipage}
At \code{n+2}, $n+1$ steps of handler runs are left, and
\m{slice_at_boundary}, which tests $\mathit{runtime} \mid n+1$, holds when they are a
whole number of runs: when the slice opens and after each
completed run inside it. Unmasking has moved here from the first stage, to boundaries
computed from the public counter. Since every run takes $\mathit{runtime}$ steps, these
are the steps on which handlers complete; only the reason has changed. At a boundary
the masks reopen, but the timer is masked again, so it cannot leave S early,
and the NOP handler becomes pending. That last step is the \emph{filler}: a handler
is always ready at a boundary, so S is entered and every run of the slice takes place
whether or not a disk interrupt is waiting. A pending disk handler takes priority;
which of the two runs is all the secret decides. At \code{1}, \m{close_slice}
closes the slice: it masks the disk and NOP handlers, so U cannot lead to S, unmasks
the timer and sets the counter to \code{0}. Since the \code{0} branch changes nothing,
the timer is never unmasked while its own handler runs.

The sliced policy is non-interfering:

\begin{theorem}[Security, \m{model_sliced_NI}]\label{thm:main}
If the scheduler and the public user process are non-interfering at
$\pubeq$ on input and output, and the private user process is
non-interfering at $\priveq$ on input and output, then
\[
\mathsf{model\_sliced}\;\mathit{runtime}\;\mathit{runs}\;p_{pub}\;p_{priv}\;p_{sched}
  \in \NI(\Ein,\, \Eout).
\]
\end{theorem}

At the attacker's level $\Lo$ the conclusion says that disk interrupts do not show: a
disk interrupt is unobservable at $\Lo$ (\cref{def:io}), so two input streams
that differ only in disk interrupts must give outputs that $\Eout$ relates.
\Cref{sec:proof} proves the theorem, as an instance of one that holds for any interrupt
policy meeting three obligations (\cref{thm:policy}).

The theorem holds for every scheduler, pair of user processes and output
types, handler length and number of handler runs per slice, provided each slot process
is non-interfering at its own classification. This rests on one property of the state
update: it reads only \emph{whether} a user slot emitted, never what, so no user
behaviour reaches the schedule.

The result carries over to the user view:

\begin{corollary}[User-view security,\newline \m{model_sliced_userview_NI}]\label{cor:userview}
Under the same hypotheses, the user view of the sliced model,
\m{model_sliced_userview}, is in $\NI(\Ein, \Euser)$.
\end{corollary}

\begin{proof}
The user view is $\mathsf{map}\;\mathsf{id}\;\mathsf{parse\_output}\;\mathsf{model\_sliced}$,
so \comp{it:map} applies with \cref{thm:main}. The input function \code{id} is trivial, and
$\mathsf{parse\_output} \in \NI(\Eout,\Euser)$ because outputs that $\Eout$ relates
agree on which user slot, if any, emitted, and on the public user's value.
\end{proof}

Under the sliced policy the disk interrupt still affects this view, through the private
user's input (\cref{sec:loop}): on the concrete system, the private user emits
\code{Sys} with a disk interrupt and \code{Idle} without (\m{trace_with_dI},
\m{trace_no_dI}), a value the attacker cannot see.
