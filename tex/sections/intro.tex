\section{Introduction}\label{sec:intro}

An operating system owns the devices, decides which process runs and when, and
stands between processes that must not learn about each other. Whatever it lets one
process observe about another is a potential leak, and that includes \emph{when}
things happen, not only what values are computed.

Interrupts are how an operating system learns that something happened: a disk
transfer completed, a packet arrived, a timer expired. Some of these events are
secret. Whether a particular process just received data from the disk may reveal
what it is doing, so an operating system that keeps such an event secret has to
hide that it happened at all.

Ordinary interrupt handling does not hide it. As soon as the interrupt can be
serviced, its handler runs, displacing whatever process was scheduled; the handler
takes a few steps, and then the displaced process resumes. Suppose a public process keeps
issuing requests whose results an attacker can see. While the handler runs, those
requests stop, and the attacker sees a gap in the stream exactly as long as the
handler (\cref{fig:leak}). The interrupt has leaked through the \emph{schedule}.
Timing leaks through interrupt handling of this kind arise in several operating
systems \todo{examples, with citations}.

This is the example we follow throughout the paper. The secret is \emph{whether a
disk interrupt occurred}. A public process issues requests whose results the
attacker sees, and a private process, the legitimate consumer of the disk event,
reacts to it. The attacker may learn nothing about the disk interrupt. \Cref{sec:model,sec:designs,sec:proof}
model this system, exhibit the leak, and remove it.

Leaks of this kind are the subject of information flow
control~\cite{sabelfeld2003}, where the absence of a leak is stated as
non-interference~\cite{goguen1982}: varying what the attacker may not see must not
change what it does see. For timing leaks, ``what it sees'' must include when each
output appears~\cite{agat2000}.

We use the process calculus of Rafnsson, Jia and Bauer~\cite{rafnsson2017}, whose
non-interference is timing-sensitive and whose theorems compose: if the parts of a
process are non-interfering at suitable equivalences, so is the whole. We model an
operating system with interrupt handling as one closed process in this calculus
(\cref{fig:system}): the user processes, the scheduler and the handlers run in a pool,
and a global state decides at each step which of them runs. We prove in Rocq that
ordinary interrupt handling is interfering (\m{model_immediate_not_NI}): the leak
of \cref{fig:leak} is a counterexample.

What the attacker learns is \emph{when} a secret handler runs and \emph{for how
long}. A non-interfering policy must therefore fix both by public events; only
\emph{which} secret handler runs may depend on the secret. We model a policy that
does so. Secret handlers run only inside time slices, each opened when the handler
of the public timer completes and each holding a fixed number of handler runs; a
run that no real interrupt claims is filled by a dummy handler, the NOP handler. A
secret handler run then replaces a NOP run instead of displacing a user process.
That this is safe is intuitive; proving it is not. The secret still changes the
state: it sets a pending bit, decides which handler fills a run, and changes what
the private user process does next. The proof must show that none of this ever
decides whether, or for how long, a secret handler runs (\cref{sec:proof}).

We prove this policy non-interfering (\m{model_sliced_NI}), even to an attacker who
sees at every step which process ran, except which of the two secret handlers.
Both policies are instances of a single generic model and differ only in their
\emph{interrupt policy}: the part that decides when handlers may run. The result is
general in two ways. It holds for every scheduler and every pair of user processes
that are themselves non-interfering. And it holds for every choice of the two
numbers that fix the timing of the policy: the number of steps one handler run
takes, and the number of handler runs that fit in one time slice.

The model fixes \emph{what} the modified interrupt processing must do; how to
implement it in an operating system is carried out in separate work

\paragraph{Contributions}
\begin{itemize}
\item A mechanised, timing-sensitive non-interference proof for interrupt handling
  (\cref{sec:designs,sec:proof}), and a mechanised counterexample for ordinary
  interrupt handling (\cref{sec:leak}). The proof is compositional: it applies one
  generic theorem per constructor of the model, which leaves two side conditions
  specific to interrupt handling, one of them hard (\cref{sec:state-equiv}).
\item Requirements, read off the proof's obligations, on any implementation of
  interrupt handling that is to be non-interfering (\cref{sec:requirements}). The
  arrival of a secret interrupt may only record that it is pending. When secret
  handlers run, and for how long, must be fixed by public events, so the time
  reserved for them must be fixed in advance and always used up. And the interrupt
  controller must be split by secrecy: which interrupts are pending is secret, while
  the masks that decide what runs next are public. The implementation in
  \todo{cite X} follows these requirements.
\item A mechanisation of the calculus and its composition theorems. Our
  definitions depart from the original in one essential place: non-interference
  is stated over finite traces, which makes every proof an induction. We prove the
  definition equivalent to the original coinductive one, so our main results also
  hold in the original's terms (\cref{sec:mechanisation}).
\end{itemize}
