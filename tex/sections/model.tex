\section{Interrupt Handling and Scheduling as One Process}\label{sec:model}
The mechanism we model is that of
Linux~\cite{love2010}\note{check Love: page reference, second source for current
kernels}. A device raises an \emph{interrupt request} (IRQ) at the
\emph{interrupt controller}, where it stays \emph{pending} while it is \emph{masked}.
The interrupt handler displaces the running process and runs with interrupts
masked\note{check: some or all interrupts?}, so it is not interrupted itself; we leave
out the work it defers to a \emph{bottom half}. The handler of the periodic
\emph{timer tick} sets the \code{need_resched} flag when the running process has used
up its time. On the \emph{return from interrupt} the kernel checks this flag: if set,
the scheduler runs; otherwise the interrupted process resumes.

Our model keeps these parts in a simpler form\note{check: state the differences? The
timer handler always sets the flag; one processor}. The interrupt controller holds a pending and a mask bit per
handler. An interrupt only sets its pending bit. A handler
can start when its pending bit is set and its mask is clear; starting it clears the
pending bit and sets all the masks. Once a handler has finished, the next handler that
can start runs. If there is none, control returns to the interrupted user process, or
goes to the scheduler if the \emph{reschedule flag}, our \code{need_resched}, is set.
We build the process from the inside out, each layer wrapping the last.

\subsection{The processes}\label{sec:processes}

The system runs six processes: three interrupt handlers, a scheduler, and two user
processes. We group them by the three kinds of step, which the rest of the
paper keeps apart:
\begin{itemize}
\item \emph{U}, a user process or the scheduler, the three parameters of the model:
  $p_{pub} : \Proc{\mathsf{Empty}}{\mathsf{Opub}}$, whose output the attacker sees;
  $p_{priv} : \Proc{\mathsf{Bool}}{\mathsf{Opriv}}$, which takes the disk handler's
  output as input; and $p_{sched} : \Proc{\mathsf{Empty}}{\mathsf{Bool}}$, whose
  output chooses which user process runs next. The private user process is why the
  disk interrupt is secret: it does the disk I/O, and is the legitimate recipient of
  the interrupt. The disk that raises an interrupt in answer to a request is part of
  the environment.
\item \emph{T}, the timer handler. The timer's interrupt is public, and both policies
  set the reschedule flag when its handler finishes, which is how control reaches
  the scheduler.
\item \emph{S}, a secret handler. The disk interrupt is the secret. The NOP handler
  belongs to no device: no interrupt raises it, it computes nothing, and the sliced
  policy uses it as filler.
\end{itemize}
The timer, disk and NOP handlers are copies of one process, a counter:
\begin{lstlisting}
ir_handler runtime :=
  map id (fun o => if o.1 == 0 then Notify
                   else Nothing)
    (sta (fun _ v => v)            (* input *)
         (fun _ v => v.+1 %% runtime) (* output *)
         0 (out tt))
\end{lstlisting}
The state cell holds a step count, which no input changes and each step advances
modulo \code{runtime}, so a handler run takes exactly \code{runtime} steps. The
handler emits \code{Notify} on the last of them to announce completion, and
\code{Nothing} otherwise.

\subsection{The pool}\label{sec:pool}

The six processes run side by side in a \emph{pool} (\cref{fig:system}), each behind
a switch controlled by the current process identifier (pid): a pid names one slot,
whose process takes one step, while every other slot emits \code{None} and takes no
output step. Each slot
(\m{process_pool}) is a
\code{swi} whose input bit says whether the pid names it, which opens its switch;
the slot tags each output with \code{true}, which closes the switch again, so a
selected process takes exactly one step.
Inside the switch a \code{maybe} makes the process's own input optional:
\m{f_proj} gives the private user the disk handler's output, and every other process,
whose input type is empty, \code{None}. A second \code{maybe} around the whole pool
lets an interrupt, which reaches the pool as \code{None}, leave it unchanged.

The pool's output records \emph{who ran} as well as what was computed, so the schedule
is part of what the system emits. Since \code{par} pairs outputs, the output is a
six-tuple, the type \m{T_out}, whose positions have types $A + 1$: \code{Some} where
the slot ran and \code{None} elsewhere, so at most one \code{Some} per step. The
system's input type \m{T_in} is a sum of the two interrupts, \code{inl} for the timer
and \code{inr} for the disk.

\subsection{The state}\label{sec:global-state}\label{sec:state}

Around the pool sits a state cell, a \code{sta} whose value and two update
functions together model the interrupt controller, along with
the remaining bookkeeping.
The global state (\m{state_type}) is the box of \cref{fig:system}
opened up: a nest of pairs holding two pids, a flag, a counter and the interrupt
controller.

\begin{itemize}
\item The \emph{current pid} names the slot that runs next. The two secret
  handlers, the S steps, sit on the \code{inl} side, \code{inl true} for the disk handler and
  \code{inl false} for the NOP handler, and every other process on the \code{inr}
  side, numbered from 0: timer handler, scheduler, private user, public user, where
  the system starts (\m{initial_pid}).
\item The \emph{previous pid}, a bit, names the user process a handler last
  displaced, which control returns to: \code{true} for the private user and
  \code{false} for the public one (\m{user_pid}).
\item The \emph{reschedule flag} is the boolean \m{re_sched}.
\item The \emph{slice counter} \m{slice_count} counts the output steps until
  the current time slice closes, and is \code{0} outside a slice; the immediate
  policy leaves it \code{0}.
\item The \emph{interrupt controller} \m{ic} holds the two bits of each handler,
  indexed by \m{irq}, of type \code{T_in}${} + 1$: \code{timer_irq} and
  \code{disk_irq} for the two interrupts and \code{nop_irq}, which is \code{None},
  for the NOP handler.
\end{itemize}

The two update functions correspond to the two kinds of step of
\cref{sec:background}. The input update $f$ records an interrupt
and decides nothing:
\begin{lstlisting}
input_update e v :=
  if e is inl i then set_pending i v else v
\end{lstlisting}
An \code{inl} event sets the arriving interrupt's pending bit (\m{set_pending}). The
event is a sum because of the loop. The output
update $g$ runs on each output of the pool; the interrupt policy acts there:
\begin{lstlisting}
output_update observe_policy advance_policy o :=
  initiate_next o \o
    (advance_policy \o observe_policy o)
\end{lstlisting}
Its first two stages, left open here, are the \emph{service policy}:
\code{observe_policy} reacts to the output, and \code{advance_policy} reads only the
state. The third, \m{initiate_next}, computes the next pid.

The next pid is chosen in two steps. \m{initiate_next} first adopts the user process
the scheduler chose, if the scheduler ran (\m{apply_scheduler_choice}): the
scheduler emits a bit, which the model maps to one of the two user pids, so no
scheduler can select a handler. It then chooses by
four rules, tried in order:
\begin{enumerate}
\item if a handler is running (all masks are set), it continues;
\item otherwise, if a handler can be started, it starts;
\item otherwise, if a handler has just finished, control returns to the user
  process it interrupted, or to the scheduler if a reschedule was requested;
\item otherwise, the current process continues.
\end{enumerate}
If several handlers can start, the order is timer, disk, NOP.
Starting a handler saves the current pid as the previous pid if it is a user
process, points the current pid at the handler, sets all masks and clears the handler's
pending bit (\m{initiate_handler}).

\subsection{The loop}\label{sec:loop}

The state now computes a next pid, but the pool cannot learn it. A switch opens only
on an input, so the next pid must reach the pool as an input, and only \code{loop}
supplies one: it feeds each output back as an input, within the same step.
\m{pool_input} turns a fed-back output \code{o} into the input
\code{Some (pid, dI_out o)}, with the state's current pid, and so does the loop's two
jobs.

The first job is to deliver the pid: without it, no switch would reopen after
the first step. The second is to give the private user, the legitimate consumer of
the disk event, the disk handler's output; this input makes the effect of the disk
handler's run visible in user space.

A \code{loop} needs equal input and output types, while the system takes
interrupts and emits tuples. So inside the loop an event is a sum, \code{T_in + T_out},
with interrupts as \code{inl} and outputs as \code{inr}. The map inside the loop tags
each output \code{inr} and drops the state that \code{sta} emits with it. When an
output comes back, $g$ has already updated the state, so \m{input_update} leaves it
alone on \code{inr}, and \m{pool_input} reads the new pid from it. An interrupt
is \code{inl}, which \m{pool_input} sends to \code{None}. The feedback is part of the
output step, so no interrupt can arrive in between.

\subsection{The generic model}\label{sec:parameters}

A last map gives the loop the system's own input and output types. Together, these
parts form the generic model, the loop of \cref{fig:system} with the pool inside the
global state, written here with the wrapper \m{reactive_system} unfolded:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
model runtime init_policy
      observe_policy advance_policy
      p_pub p_priv p_sched : Proc T_in T_out :=
  map inl (inr_or_def no_output)
   (loop (map id (fun x => inr x.2)
    (sta input_update
     (output_update observe_policy advance_policy)
     init_policy
     (map pool_input id (maybe
      (pool runtime p_pub p_priv p_sched))))))
\end{lstlisting}
\end{minipage}
The outer \code{map} tags an arriving interrupt \code{inl}, and \m{inr_or_def}
strips the \code{inr} tag from each output. Its
default \m{no_output}, the all-\code{None} tuple, only makes it total.

Apart from the processes and the handler length, everything in
\cref{sec:processes,sec:pool,sec:global-state,sec:loop} is fixed except three parts,
marked \code{_policy}. The masks of the initial state \code{init_policy}
decide which interrupts can be serviced before anything has happened.
\code{observe_policy} and \code{advance_policy}, the service policy of
\cref{sec:state}, reopen the masks, and so decide when the next handler becomes
eligible. Together they decide \emph{when a handler may run}, and we call them the
\emph{interrupt policy}.
