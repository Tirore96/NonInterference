\section{An Operating System as One Process}\label{sec:model}

\Cref{sec:background} gave us a calculus of processes, equivalences that say what
an observer at each level sees, and one composition theorem per constructor. We now
use the calculus to write an operating system with interrupt handling as a single
process, following the example of \cref{fig:leak}: the secret is whether a disk
interrupt occurred. We first introduce the processes the system runs and
the pool in which they run (\cref{sec:pool}), and what the system receives and
emits (\cref{sec:interface}). We then describe the state
(\cref{sec:global-state}) and how each event updates it, ending in the choice of
who runs next (\cref{sec:state}). The resulting generic model leaves two parts
open, which together form the \emph{interrupt policy} (\cref{sec:parameters});
\cref{sec:designs} fills them twice.

\subsection{The processes and the pool}\label{sec:pool}

The system runs six processes: three interrupt handlers, a scheduler, and two user
processes. The timer, disk and NOP handlers are copies of one process, a counter:
\begin{lstlisting}
ir_handler runtime :=
  map id (fun o => if o.1 == 0 then Notify
                   else Nothing)
    (sta (fun _ v => v)                  (* input *)
         (fun _ v => v.+1 %% runtime)    (* output *)
         0 (out tt))
\end{lstlisting}
The state cell holds a step count, which no input changes and each step advances
modulo \code{runtime}. So a handler run takes exactly \code{runtime} steps, and on
its last step the handler emits \code{Notify} to announce completion, and
\code{Nothing} on the others. The public user process issues requests
(\code{Get}) whose results the attacker sees. The private user process takes the
disk handler's output as input, and emits \code{Sys} when it has been notified of a
disk event and \code{Idle} otherwise. When the scheduler runs, it proposes which
user process runs next.

The six processes run side by side in a \emph{pool} (\cref{fig:system}), and only
one of them takes a step at a time. Each sits behind a switch, controlled by the
current process identifier (pid): a pid names one slot, whose process takes one
step, while every other slot emits \code{None} without moving. Each slot is a
\code{swi} whose input bit says whether the pid names it, which opens its switch;
the slot tags each output with \code{true}, which closes the switch again, so a
selected process takes exactly one step (\cref{fig:semantics}). The pid is held in a
global state, which a state cell and a feedback loop thread around the pool
(\m{reactive_system}, \cref{sec:parameters}).

\subsection{Inputs and outputs}\label{sec:interface}

The system receives interrupts. Its input type \code{T_in} is a sum, like the
current pid of \cref{sec:global-state}: \code{inl} is the disk interrupt and
\code{inr} the timer interrupt. An interrupt goes to the state
(\cref{sec:global-state}), where it marks itself pending in the interrupt
controller.

By the rule for \code{par} (\cref{fig:semantics}), the pool emits the
outputs of all its slots together. So the system emits a six-tuple
whose positions have types $A + 1$, with \code{Some} where the slot ran and
\code{None} elsewhere, the output type \code{T_out}, with exactly one \code{Some} on
each step. The output therefore
records not only what was computed but also \emph{who ran}: the schedule is part of
what the system emits. The steps it records are of three kinds, which the rest of the
paper keeps apart: \emph{U}, a user process or the scheduler; \emph{T}, the timer
handler; and \emph{S}, a secret handler, disk or NOP.

\begin{definition}[Input and output equivalences]\label{def:io}
The input equivalence $\Ein$ (\m{in_equiv}) and the output equivalence $\Eout$
(\m{out_equiv}) are
\begin{alignat*}{2}
\Ein &\triangleq{} && \priveq + \pubeq, \\
\Eout &\triangleq{} && \hphantom{{}\times{}}(\pubeq + \one^\Lo) \\
&&& {}\times (\priveq + \one^\Lo) \\
&&& {}\times (\pubeq + \one^\Lo) \\
&&& {}\times (\priveq + \one^\Hi) \\
&&& {}\times (\priveq + \one^\Hi) \\
&&& {}\times (\pubeq + \one^\Lo),
\end{alignat*}
one factor per slot, in the order public user, private user, scheduler, NOP,
disk and timer handler, with $\times$ associating to the right, as the output
nests.
\end{definition}

The disk interrupt is thus hidden from the attacker, and the timer interrupt is
public. Of each output the attacker sees whether the slot ran and its value on the
dark slots of \cref{fig:system}, only whether it ran on the light slot, and nothing
on the white ones.
So the attacker sees the U and T steps, and of an S step only that it happened: no
other slot ran. \Cref{sec:gating} shows that the proof forces this shape. Each
output, like each input, then updates the state.

The \emph{user view} keeps only the two user slots, as one
value of type \code{(Opub + Opriv) + 1}:
\begin{lstlisting}
parse_output o :=
  match o with
  | (Some v, _)         => Some (inl v)
  | (None, (Some v, _)) => Some (inr v)
  | _                   => None
  end
userview m := map id parse_output m
\end{lstlisting}

\begin{definition}[Visible equivalence]\label{def:visible}
The visible equivalence $\doteq^\circ$ (\m{eqvisible}) of an equivalence $\doteq$
relates what $\doteq$ relates and hides nothing:
\[
x \doteq^\circ_\ell y \iff x \doteq_\ell y,
  \qquad x \doteq^\circ_\ell \unobs \text{ never}.
\]
\end{definition}

At $\Lo$ a private-user output and \code{None} are both hidden, so a plain sum
would relate them and hide whether the private user ran. Under a sum, $^\circ$
keeps the tag visible, so the user view applies it to the private user's
equivalence.

\begin{definition}[User-view equivalence]\label{def:userview}
The user-view equivalence $\Euser$ (\m{out_equiv_userview}) is
\[
\Euser \triangleq (\pubeq + \privvis) + \one^\emptyset,
\]
writing $\privvis$ for $(\priveq)^\circ$.
\end{definition}

So the attacker still sees when the private user runs. The user view thus erases only public
information: the scheduler and the timer handler, and which of them, or S, ran.

\subsection{The state}\label{sec:global-state}

The global state (\m{state_type}, \cref{fig:state}) is the box of \cref{fig:system}
opened up: a nest of pairs holding two pids, two flags and the interrupt controller.

\begin{itemize}
\item The \emph{current pid} names the slot that runs next. The two secret
  handlers, the S steps, sit on the \code{inl} side, \code{inl true} for the disk handler and
  \code{inl false} for the NOP handler, and every other process on the \code{inr}
  side, numbered from 0: timer handler, scheduler, private user, public user. The
  system starts in the public user (\m{initial_pid}).
\item The \emph{previous pid} is the user process a handler interrupted, to which
  control returns when the handler finishes.
\item The \emph{reschedule flag} \m{re_sched} sends control to the scheduler
  instead, when a handler finishes.
\item The \emph{slice counter} \m{slice_count} counts the steps left in the current
  time slice, for the sliced policy (\cref{sec:sliced}); the ordinary policy leaves
  it \code{None}.
\item The \emph{interrupt controller} \m{ic} holds a pending bit and a mask bit
  for each handler. Its entries are indexed by \m{irq}, of type
  $\mathit{Interrupt} + 1$:
  \code{timer_irq} and \code{disk_irq} for the two interrupts, and
  \code{nop_irq}, which is \code{None}, for the NOP handler. No interrupt raises
  the NOP entry; the sliced policy sets it pending itself, to use the NOP handler
  as filler.
\end{itemize}
The initial state is not fixed here: it is part of the interrupt policy
(\cref{sec:parameters}).

The state changes on both kinds of step of \cref{sec:background}, through
\m{state_step}; under each stage are the fields of \cref{fig:state} it writes:

\end{center}
On an input step, \m{set_pending} sets the arriving interrupt's pending bit and
nothing else happens: the pool idles and nothing is emitted. On an output step, the
pool's output is fed back to the state, where three stages run in turn.
\m{check_scheduler} adopts the pid the scheduler proposed, if the scheduler ran. The
next stage, \code{service_policy}, is left open here: it is half of the interrupt
policy (\cref{sec:parameters}), and \cref{sec:designs} fills it twice. Last,
\m{initiate_next} computes the next pid. (In the code the state receives both kinds
of event as one sum, interrupts as \code{inl} and fed-back outputs as \code{inr}
(\cref{sec:parameters}), and \code{step_sum} dispatches on the tag.)


A handler can be started when its controller entry is pending and not masked; if
several can, the timer goes first, then the disk, then NOP. Handlers cannot be
interrupted: starting one sets all masks, and the service policy unsets them when the
handler finishes. \m{initiate_next} chooses by four rules, tried in order:
\begin{enumerate}
\item if a handler is running (all masks are set), it continues;
\item otherwise, if a handler can be started, it starts;
\item otherwise, if a handler has just finished, control returns to the user
  process it interrupted, or to the scheduler if a reschedule was requested;
\item otherwise, the current process continues.
\end{enumerate}
In the code, with the rules marked:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
initiate_next restore_invariant v =
  if masks_set v then v            (* rule 1 *)
  else let v := restore_invariant v in
    if first_ready v is Some ir
    then initiate_handler ir v     (* rule 2 *)
    else if is_handler_pid v       (* rule 3 *)
    then if get_re_sched v
         then initiate_scheduler v
         else initiate_prev_pid v
    else v                         (* rule 4 *)
\end{lstlisting}
\end{minipage}
\m{first_ready} picks the first handler that can be started, in the order above.
\m{initiate_handler} saves the current pid as the previous pid, unless it is a
secret handler, points the current pid at the handler, sets all masks and clears
the handler's pending bit. \m{initiate_scheduler} hands control to the scheduler and
clears \m{re_sched}; \m{initiate_prev_pid} returns to the previous pid. Between
rules 1 and 2, \m{initiate_next} applies \m{restore_invariant}, a hook used only by
the proof (\cref{sec:parameters}).

Rule 2 is the source of the leak of \cref{fig:leak}, as \cref{sec:leak} shows step by step.

\subsection{The generic model}\label{sec:parameters}

Together, these parts form the generic model, the pool inside the global state:
\begin{lstlisting}
model runtime init_policy service_policy
      restore_invariant p_pub p_priv p_sched =
  reactive_system init_policy
    (state_step service_policy restore_invariant)
    no_output
    (pool runtime p_pub p_priv p_sched)
    pool_input
  : Proc T_in T_out
\end{lstlisting}
Its first argument, \code{runtime}, is the handler length, and its last three are
the user processes and the scheduler; the user processes' output types, also
arguments, are left implicit. The wrapper \m{reactive_system} is the loop of
\cref{fig:system}, built from the constructors of \cref{fig:semantics}:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
reactive_system state state_update
                no_output p pool_input =
  map inl (inr_or_def no_output)
    (loop (map id snd
      (sta state_update (fun _ v => v) state
        (map pool_input inr (maybe p)))))
\end{lstlisting}
\end{minipage}
Inside the loop an event is a sum: the outer \code{map} tags an arriving interrupt
\code{inl}, and the inner \code{map} tags each output of the pool \code{inr}, which
\code{loop} feeds back. The \code{sta} cell is the global state, updated by
\code{state_update} on every event and left alone on an output. \m{pool_input}
gives the pool the new current pid, and the private user the disk handler's output,
after a fed-back output, and \code{None} after an interrupt, on which \code{maybe}
leaves the pool unchanged. On the way out, \code{map id snd} drops the state that
\code{sta} emits with each output, and \m{inr_or_def} strips the \code{inr} tag. Its
default \m{no_output}, the all-\code{None} tuple, only makes it total: every output
is tagged \code{inr}.

Apart from the processes and the handler length, everything in
\cref{sec:pool,sec:interface,sec:global-state,sec:state} is fixed, except two
parts, marked by the suffix \code{_policy}:
\begin{itemize}
\item \code{init_policy}, the initial state, a value of the type of
  \cref{sec:global-state}. Its masks decide which interrupts can be serviced before
  anything has happened.
\item \code{service_policy}, the open stage of \cref{sec:state}. It is the stage
  that reopens masks, and so decides when the next handler becomes eligible.
\end{itemize}
Together they decide \emph{when a handler may run}, and we call them the
\emph{interrupt policy}. The remaining argument, \m{restore_invariant}, is not part
of it. It writes into the state an invariant that the policy already maintains,
for the benefit of the proof (\cref{sec:restore}); it never changes a state the
model reaches (\cref{thm:noop}), and it is the identity where the proof needs no
help. \Cref{sec:designs} fills the two parts of the interrupt policy twice.

The model is parametric in more than the policy. The scheduler, the two user
processes and their output types are arguments, as is the handler length; the sliced
policy adds the number of handler runs per slice. \Cref{thm:main} holds for all of
them, provided each slot process is non-interfering at its own classification: the
mechanism cannot make a leaking process secure, only add no leak of its own. The
handler length and slice size need no condition, because a slice is defined as
$\mathit{runs}\cdot\mathit{runtime}$ steps and so ends on a handler boundary. This
generality rests on one property of the state update: it reads only \emph{whether} a
user slot emitted, never what, so no user behaviour reaches the schedule. What is
fixed is the mechanism under study: the three handlers, and the six slots in the
order the state update reads them.
