\section{An Operating System as One Process}\label{sec:model}
We now write an operating system with interrupt handling as a single process,
following the example of \cref{fig:leak}. After describing the interrupt mechanism
without the calculus (\cref{sec:interrupts}), we build the process from the inside
out, each layer wrapping the last; \cref{sec:parameters} gives the whole term.

\subsection{Interrupt handling}\label{sec:interrupts}

The machine runs one process at a time. A device signals an interrupt by
setting its \emph{pending} bit in the \emph{interrupt controller}, and at that moment
nothing else happens. An \emph{interrupt handler} is a process the system starts on
the device's behalf. It can start when its pending bit is set and its \emph{mask} bit
is clear, and starting it clears the pending bit.

Starting a handler also sets all the masks, so handlers are non-preemptive:
a running handler is never interrupted, and an interrupt that arrives meanwhile stays
pending until the masks reopen. When the masks reopen is what the two policies of
\cref{sec:designs} disagree on. Once a handler has finished, control goes to the next
handler that can start. If there is none, it returns to the user process that was
interrupted, or goes to the scheduler if the \emph{reschedule flag} is set.

There are two devices. The timer drives scheduling: when its handler
finishes it sets the reschedule flag, which is how control reaches the scheduler. Its
interrupt is public. The disk interrupt is the secret. A third handler, NOP, belongs
to no device: no interrupt raises it, and it computes nothing. The sliced policy
uses it as filler.

\subsection{The processes}\label{sec:processes}

The system runs six processes: three interrupt handlers, a scheduler, and two user
processes. We group them by the three kinds of step, which the rest of the
paper keeps apart:
\begin{itemize}
\item \emph{U}, a user process or the scheduler. The public user process issues
  requests (\code{Get}) whose results the attacker sees. The private user process
  takes the disk handler's output as input, and emits \code{Sys} when it has been
  notified of a disk event and \code{Idle} otherwise. When the scheduler runs, it
  proposes which user process runs next.
\item \emph{T}, the timer handler.
\item \emph{S}, a secret handler, disk or NOP.
\end{itemize}
The timer, disk and NOP handlers are copies of one process, a counter:
\begin{lstlisting}
ir_handler runtime :=
  map id (fun o => if o.1 == 0 then Notify
                   else Nothing)
    (sta (fun _ v => v)            (* input *)
         (fun _ v => v.+1 %% runtime) (* output *)
         0 (out tt))
\end{lstlisting}
The state cell holds a step count, which no input changes and each step advances
modulo \code{runtime}. So a handler run takes exactly \code{runtime} steps, and on
its last step the handler emits \code{Notify} to announce completion, and
\code{Nothing} on the others.

\subsection{The pool}\label{sec:pool}

The six processes run side by side in a \emph{pool} (\cref{fig:system}), and only
one of them takes a step at a time. Each sits behind a switch, controlled by the
current process identifier (pid): a pid names one slot, whose process takes one
step, while every other slot emits \code{None} without moving. Each slot
(\m{process_pool}) is a
\code{swi} whose input bit says whether the pid names it, which opens its switch;
the slot tags each output with \code{true}, which closes the switch again, so a
selected process takes exactly one step.
Inside the switch a \code{maybe} makes the process's own input optional:
\m{f_proj} gives the private user the disk handler's output, and every other process,
whose input type is empty, \code{None}.

Since \code{par} emits both outputs as a pair, the pool emits a six-tuple
whose positions have types $A + 1$, with \code{Some} where the slot ran and
\code{None} elsewhere, the output type \code{T_out}, with exactly one \code{Some} on
each step. The output therefore
records not only what was computed but also \emph{who ran}: the schedule is part of
what the system emits.

Around the whole pool sits a second \code{maybe}, so that an interrupt, which
reaches the pool as \code{None}, leaves it unchanged.

\subsection{The state}\label{sec:global-state}\label{sec:state}

Around the pool sits a state cell, a \code{sta} whose value and two update
functions together model the interrupt controller of \cref{sec:interrupts}, along with
the remaining bookkeeping.
The global state (\m{state_type}) is the box of \cref{fig:system}
opened up: a nest of pairs holding two pids, two flags and the interrupt controller.

\begin{itemize}
\item The \emph{current pid} names the slot that runs next. The two secret
  handlers, the S steps, sit on the \code{inl} side, \code{inl true} for the disk handler and
  \code{inl false} for the NOP handler, and every other process on the \code{inr}
  side, numbered from 0: timer handler, scheduler, private user, public user. The
  system starts in the public user (\m{initial_pid}).
\item The \emph{previous pid}, a number or \code{None}, is the user process a handler
  interrupted.
\item The \emph{reschedule flag} is the boolean \m{re_sched}.
\item The \emph{slice counter} \m{slice_count} counts the output steps until
  the current time slice closes, and is \code{0} outside a slice; the ordinary
  policy leaves it \code{0}.
\item The \emph{interrupt controller} \m{ic} holds the two bits of
  \cref{sec:interrupts} for each handler. Its entries are indexed by \m{irq}, of type
  $\mathit{Interrupt} + 1$:
  \code{timer_irq} and \code{disk_irq} for the two interrupts, and
  \code{nop_irq}, which is \code{None}, for the NOP handler.
\end{itemize}

The two update functions correspond to the two kinds of step of
\cref{sec:background}. The input update $f$ records an interrupt
and decides nothing:
\begin{lstlisting}
input_update e v :=
  if e is inl i then set_pending i v else v
\end{lstlisting}
\m{set_pending} sets the arriving interrupt's pending bit. Its argument is a
sum because of the loop, and \cref{sec:loop} explains the \code{inr} case. The output
update $g$ runs on each output of the pool, and is where the interrupt policy acts:
\begin{lstlisting}
output_update observe_policy advance_policy o :=
  initiate_next o \o
    (advance_policy \o observe_policy o)
\end{lstlisting}
Its first two stages together are the \emph{service policy}, and are left
open here. \code{observe_policy} reacts to what the output says, and
\code{advance_policy} reads only the state. The third stage,
\m{initiate_next}, computes the next pid.

If several handlers can start, the timer goes first, then the disk, then NOP.
\m{initiate_next} first adopts the pid the scheduler
proposed, if the scheduler ran (\m{apply_scheduler_choice}), and then chooses by
four rules, tried in order:
\begin{enumerate}
\item if a handler is running (all masks are set), it continues;
\item otherwise, if a handler can be started, it starts;
\item otherwise, if a handler has just finished, control returns to the user
  process it interrupted, or to the scheduler if a reschedule was requested;
\item otherwise, the current process continues.
\end{enumerate}
Starting a handler saves the current pid as the previous pid, unless it is a secret
handler, points the current pid at the handler, sets all masks and clears the handler's
pending bit (\m{initiate_handler}).

\subsection{The loop}\label{sec:loop}

So far the state computes a next pid, but the pool has no way to learn it. A
switch opens only on an input, so after an output the next pid
must reach the pool as an input, and only \code{loop} supplies one: it feeds each
output back as an input, within the same step. \m{pool_input} turns a fed-back output
\code{o} into the input \code{Some (pid, dI_out o)}, with the current pid of the state,
and so does the loop's two jobs.

The first job is to deliver the pid: without it, no switch would reopen after
the first step. The second is to give the private user the disk handler's output. The
private user is the legitimate consumer of the disk event, and this input is what makes
the effect of the disk handler's run visible in user space (\cref{sec:leak}).

\code{loop} needs equal input and output types, while the system takes
interrupts and emits tuples. So inside the loop an event is a sum, \code{T_in + T_out},
with interrupts as \code{inl} and outputs as \code{inr}. The map inside the loop tags
each output \code{inr} and drops the state that \code{sta} emits with it. When an
output comes back, $g$ has already updated the state, so \m{input_update} leaves the
state alone on \code{inr}, and \m{pool_input} reads the new pid from it. An interrupt
is \code{inl}, which \m{pool_input} sends to \code{None}. The feedback is part of the
output step, so no interrupt can arrive between the update and the feedback.

\subsection{The generic model}\label{sec:parameters}

A last map gives the loop the system's own input and output types. Together, these
parts form the generic model, the loop of \cref{fig:system} with the pool inside the
global state, written here with the wrapper \m{reactive_system} unfolded:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
model runtime init_policy
      observe_policy advance_policy
      p_pub p_priv p_sched : Proc T_in T_out =
  map inl (inr_or_def no_output)
   (loop (map id (fun x => inr x.2)
    (sta input_update
     (output_update observe_policy advance_policy)
     init_policy
     (map pool_input id (maybe
      (pool runtime p_pub p_priv p_sched))))))
\end{lstlisting}
\end{minipage}
The outer \code{map} tags an arriving interrupt \code{inl}, and \m{inr_or_def}
strips the \code{inr} tag from each output. Its
default \m{no_output}, the all-\code{None} tuple, only makes it total: every output
is tagged \code{inr}.

The first argument, \code{runtime}, is the handler length, and its last three are
the user processes and the scheduler; the user processes' output types, also
arguments, are left implicit.

Apart from the processes and the handler length, everything in
\cref{sec:processes,sec:pool,sec:global-state,sec:loop} is fixed, except three parts,
marked by the suffix \code{_policy}. The masks of the initial state \code{init_policy}
decide which interrupts can be serviced before anything has happened.
\code{observe_policy} and \code{advance_policy}, the service policy of
\cref{sec:state}, reopen the masks, and so decide when the next handler becomes
eligible. Together they decide \emph{when a handler may run}, and we call them the
\emph{interrupt policy}. \Cref{sec:designs} fills them twice.
